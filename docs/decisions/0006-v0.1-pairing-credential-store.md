# ADR 0006: Version 0.1 Pairing And Credential Store

- Status: accepted; Admin presentation amended by ADR 0012
- Date: 2026-08-31

## Context

Apple TV pairing returns long-term private key material. The disposable PoC
stored base64 JSON in an owner-only but unencrypted file; ADR 0004 explicitly
forbids reusing that mechanism in the adapter. Pairing also needs an interactive
Admin flow without ever placing the PIN or credentials in ordinary states,
configuration logs, or callbacks.

The central ioBroker credential manager is designed for user-created login or
key records and exposes no adapter write API for protocol-generated structured
credentials. It is therefore not the correct persistence boundary for this
flow.

## Decision

Store a versioned credential database in the adapter instance directory returned
by `getAbsoluteInstanceDataDir(adapter)`. Serialize the complete database as
JSON, encrypt the whole payload with the ioBroker installation secret through
`adapter.encrypt()`, and persist only a versioned encrypted envelope. Create the
directory with owner-only mode `0700` and the file with mode `0600`. Writes use
a same-directory temporary file and atomic rename; plaintext is never written
to disk.

The encrypted payload maps normalized Apple TV device IDs to the five SDK
credential fields. Binary values are canonical base64. Loads validate the
envelope, decrypted schema, identifiers, and base64 before returning data.
Corrupt or undecryptable storage fails closed and never falls back to an
unprotected format.

Pairing is available only through adapter messages while the instance is
running:

- `listPairingCandidates` returns display labels and stable device IDs from the
  latest filtered discovery;
- `startPairing` accepts one discovered device ID, starts one bounded SDK
  pairing session, and causes the Apple TV to display a PIN;
- `finishPairing` accepts the same device ID and exactly four PIN digits,
  completes pairing, persists credentials, and starts the normal connection;
- `cancelPairing` aborts and removes the active session;
- `getPairingStatus` returns a non-secret status, the active stable device ID
  while a session exists, and a stable error code;
- `listPairedDevices` and `getPairedDevicesOverview` enumerate every encrypted
  pairing, including currently offline devices, with non-secret connection and
  app-count summaries;
- `removePairedDevice` accepts one paired device ID, atomically removes its
  encrypted credentials, disconnects the local backend, and recursively removes
  the complete adapter-owned device object tree.

At most one pairing session exists per adapter instance. It expires after 120
seconds and is aborted on timeout, replacement, adapter unload, or error. The
PIN exists only in the incoming message and the active call stack. Neither PIN
nor credentials may be logged, returned, written to a state, or included in a
raw error.

The Admin configuration invokes these messages through the custom table
component accepted by ADR 0012. The PIN exists only in that component's local
memory and the active message call; it is never copied into native adapter
configuration. `common.messagebox` is enabled. Responses contain only
non-secret inventory/status fields and stable errors.

Removing a pairing rewrites the encrypted database without that record. Adapter
uninstallation follows ioBroker instance-data cleanup behavior. Host migration
requires an ioBroker backup containing both the instance directory and the
installation secret; copying the encrypted file alone is insufficient.

Removal is deliberately a local forget operation. It does not claim to remove
the controller record retained by tvOS; users can revoke that record separately
in the Apple TV settings. The Admin action requires an explicit confirmation,
and later discovery presents the device as a new pairing candidate without
recreating its public object tree.

## Consequences

Protocol-generated credentials remain outside public objects and npm package
contents, survive adapter updates/restarts, and are encrypted at rest using the
ioBroker installation boundary. A system administrator with access to the
installation secret can decrypt them, which is consistent with ioBroker's
configuration-secret model.

The implementation must not import or migrate the PoC plaintext credential
file automatically. The test device must be paired once through the real v0.1
Admin/message flow before that flow is considered working.

## Validation

Unit tests verify encryption boundaries, round-trip, schema rejection, atomic
replacement, permissions, multiple devices, deletion, and no plaintext on disk.
Adapter tests verify message validation, timeout/cancel/unload cleanup, secret
redaction, offline paired-device enumeration, confirmed local removal, object
tree cleanup, restart reload, and that no credential or PIN state exists. A
real-device test on a Linux aarch64 ioBroker host must pair, restart, reconnect,
execute a command, and unload cleanly.
